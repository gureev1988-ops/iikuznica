# Проверка черновиков Gemma с Perplexity Decider Flash

Сравниваем поведение до и после проверки на одних и тех же 35 рабочих вопросах. Исходные черновики Gemma 4 26B и пять пунктов после гибридного поиска зафиксированы в [предыдущем прогоне](../rerank/results/analysis.md). Оставшиеся 15 вопросов банка отложены для отдельной проверки.

## Запуск

Из корня репозитория в окружении с Python 3.9+ под Linux или macOS и переменной OPENROUTER_API_KEY выполни:

    python3 eval/decider/run.py

Для проверки исходных данных без сети выполни:

    python3 eval/decider/run.py --check

Скрипт сверяет хеш каждого исходного запроса. Для судьи использует модель `perplexity/pplx-decider-flash-v1.3:free` и [Decisions API](https://openrouter.ai/docs/guides/features/decisions). Повторные ответы строит та же Gemma через API из первого прогона. Эталонные действия и эталонные пункты доступны только при оценке. Размер выборки, порог 0,5 и контрольные случаи зафиксированы до вызова судьи. Порог экспериментальный.

## Что увидит сотрудник

1. Судья получает вопрос, найденные пункты и черновик. Он выбирает действие и оценивает обоснованность и полноту. Код разрешает показ прямого ответа, если обе оценки достигли порога и все его ссылки однозначно сопоставились с переданными пунктами.
2. Когда выбор правила зависит от сотрудника, код показывает уточняющий вопрос по выбранному судьёй признаку. Для эскалации он предлагает обратиться в службу качества. Прогон проверяет текст и действие интерфейса.
3. При нехватке источников код запрашивает соседние пункты тех же разделов и дополнительные результаты ранжирования. При недостатке самого черновика сохраняет исходные источники. В обоих случаях Gemma получает одну попытку переписать ответ, затем судья проверяет его повторно. Если снова требуется доработка, сотрудник получает предложение обратиться в службу качества.

## Что сохранить после запуска

В каталоге `eval/decider/results/` появятся `manifest.json`, ответы обоих API в `calls/`, окончательные тексты и ссылки в `outcomes.jsonl`, сравнение действий в `paired.csv` и итог в `summary.json`. Признак полного прогона — 35 строк и `complete: true`. После ошибки API повтори ту же команду. Каждый успешно завершённый и разобранный вызов восстанавливается по хешу. При смене кода или данных укажи другой каталог через `--out`.

Для интерпретации результатов:

- Проверь, сколько исходных ошибок прошло с первого раза на Q01/Q10/Q11/Q14/Q20/Q22/Q32. Для контроля лишних задержек смотри Q02/Q09/Q18/Q28/Q30/Q44. Это группы из предыдущего разбора, а не оценка частоты ошибок на реальном потоке.
- Проверь финальные тексты. На Q10 нужно перенести оговорку о времени для подрядчика. На Q22 проверь условия старта и обязательное согласование по ДБРЦТ 8.4–8.8. Уточнения Q01/Q11/Q14/Q32 должны запросить недостающее без преждевременного совета. На Q20 проверь предложение обратиться в службу качества. Блокировка черновика сама по себе ещё не означает, что финальная реплика верна.
- Время и стоимость посчитаны для успешных API-вызовов, без локального поиска, интерфейса и пауз между запусками. Сумма времени первой генерации и новых вызовов объединяет два разных запуска. Если провайдер не вернул стоимость, итоговое поле расходов остаётся пустым. Финальный стенд в закрытом контуре потребует отдельного замера.
