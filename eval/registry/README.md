## Запуск в Codex

Выбери репозиторий `gureev1988-ops/iikuznica`, ветку `main` и окружение `iikuznica` с `OPENROUTER_API_KEY`. Из корня репозитория выполни:

```sh
python3 eval/registry/run.py --run
```

Готовый текст для задачи в Codex:

> Запусти `python3 eval/registry/run.py --run` из корня репозитория. При временной ошибке повтори ту же команду в той же рабочей копии. По завершении сверь спорные оценки с текстами в `eval/registry/results/review.md`, запиши свой вывод и открой PR с файлами из `eval/registry/runs/start12/`. Приведи полноту оснований, число приемлемых ответов, пропущенные исключения, лишние эскалации, полную задержку генерации и расходы каждого этапа. При провале калибровки приложи вывод контроля и остановись до проверки остальных норм. Закрытую выборку оставь для отдельного финального прогона.

Для проверки с чистой копии без подключения к API:

```sh
python3 eval/registry/run.py --check
```

Нужен Python 3.9+ на Linux или macOS. Сборка реестра и все вызовы моделей используют стандартную библиотеку Python. Для нового замера BM25 нужны Node.js 22+ и пакет PGlite из зафиксированного `package-lock.json`. Онлайн-команда сама пробует установить пакет. Если установка недоступна, на рабочих 12 вопросах используется уже опубликованная выдача BM25, сквозное время для контрольного варианта в этом случае останется пустым. Офлайн-команда пакет из сети не устанавливает.

## Что измеряет прогон

1. **Подготовка источников.** Четыре независимые сессии Codex извлекли нормы каждая из своего документа, без доступа к вопросам и эталонам. В TSV хранятся номер пункта, самостоятельное утверждение с условиями и список связанных пунктов. Один пункт может содержать несколько утверждений. Исходные документы и их SHA-256 зафиксированы в [манифесте редакций](versions.json). Команда сборки сверяет исходные байты, номера, связи, покрытие всех содержательных пунктов и присоединяет точный текст основания. Полный реестр для программы создаётся в `eval/registry/claims.jsonl`. Изменённая редакция требует пересмотра разметки.
2. **Проверка записи.** Qwen3.5-122B-A10B независимо проверяет смысл каждого утверждения и покрытие каждого пункта в обратную сторону. Судья также рассматривает 40 пар, отобранных по лексической близости из корпуса. Сначала он должен различить настоящий конфликт и разные дирекции на двух изолированных контрольных примерах. Результат — список открытых вопросов владельцу с исходными пунктами. Реестр не присваивает себе полномочий разрешать спор. Отсутствие флагов у этих 40 пар оставляет остальные пары непроверенными.
3. **Поиск.** В первом варианте BM25 ищет в оригиналах. Во втором поиск использует формулировки норм, область действия, заголовки и оригиналы, затем подтягивает связанные пункты. Если оснований мало, вызывается поиск по оригиналам. Открытый спор помечается для службы качества. В обоих путях генератор получает до пяти исходных пунктов, одну версию системной инструкции и один текст вопроса. Оценивается весь вариант поиска, включая различия ранжирования. Отдельного доказательства эффекта только от формата хранения этот опыт не даёт.
4. **Генерация и проверка ответа.** Gemma 4 26B A4B IT отвечает на 12 вопросов в обоих вариантах с чередованием порядка. После генерации отдельный проход Qwen получает каждую реплику без обозначения способа поиска. Он проверяет указания, их применимость, подтверждение процитированными пунктами, потери условий и лишние эскалации. Оператор может проверить вердикт по оригиналам. При открытом конфликте реестровый вариант показывает предложение эскалации с пунктами. Для сопоставимости генератор также выполняется в фоне, в отчёте этот вызов обозначен как теневой.

При первом полном запуске запланированы **77 вызовов** для подготовки реестра, **24** для парной генерации и **24** для оценки готовых ответов. Повторы учитываются в расходах. Цена первоначальной разметки четырьмя сессиями Codex отдельно не измерялась. Оценка готовых ответов измеряет качество эксперимента и не добавляется к стоимости пользовательского запроса. Локальный поиск не вызывает LLM. Время до первого токена и завершения генерации измерено у провайдера. Сумма времени прогретого поиска и генерации служит оценкой задержки до вывода в интерфейсе.

## Результаты и повтор запуска

После полного опыта компактный отчёт для коммита находится в `eval/registry/runs/start12/REPORT.md`. Рядом лежат таблицы по вопросам, оценка ответов, открытые флаги и расходы. Подробные журналы попыток, выданные пункты и запросы на проверку сохраняются локально в `eval/registry/results/`. При сбое успешные вызовы с теми же входными данными используются повторно. Смена модели, исходников или запроса требует отдельного прогона. Офлайн-проверка пишет в отдельную папку `results/preflight/`.

Если судья не различил контрольные случаи, полный результат регистрации не считается полученным. В `results/judge/decisions.json` останется фактический вердикт. Команда останавливается перед остальными расходами на проверку реестра. При проблеме с ключом или соединением проверь доступ к OpenRouter и повтори ту же команду в том же окружении.

**Критерий выбора.** На вопросах, где основание существует, сравниваем долю ответов с верным действием, без неподтверждённых указаний и со всеми существенными оговорками. Сверяем спорные оценки по оригиналу. При улучшении качества проверяем задержку и стоимость, включая обновление реестра. Двенадцать рабочих вопросов дают диагностику. Для перехода к основному пути требуется проверка на отложенных вопросах.
