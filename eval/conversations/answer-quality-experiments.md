# Когда сотруднику можно показать инструкцию

Первым проверяем, можно ли остановить неверную инструкцию, даже когда поисковая выдача и ссылка правильные. Затем считаем, сколько корректных ответов удалось показать и сколько сотрудников зря отправили в службу качества. Ниже восемь гипотез. A1–A5 подготовила Астра, K1–K3 добавлены по итогам независимого проектирования. Каждая меняет один слой или одну проверку. Пороги приёмки предложены для эксперимента. Результатов у новых вариантов пока нет.

## Единый протокол

1. Зафиксировать контроль C на SHA `b18f988ae1754894cd5b599cfdd0a6f31352ea79` (#25) либо на более свежем проверенном SHA той же ветки, если к началу серии уже подтверждена правка P03/P10. Указать фактическую ссылку в отчёте. Сначала воспроизвести его отдельно от каждого изменения. По инструкциям в [отчёте #25](reasoning-results.md) запустить `reasoning_trial.py --compare-histories` для P03/P10 с двумя подлинными историями #24, затем `--winner C` для 42 ходов и отдельно с `--working50` для 50 одиночных. Нужны закрытый рабочий пакет, трассы для перекрёстного опыта, фиксированный MiniLM, Python с ONNX и доступ к моделям для отсутствующих вызовов. Отсутствующую историю пометить как недоступную. Исторические числа #24 не переносить на #25.
2. Каждая ветвь опыта меняет только один указанный слой относительно #25. Закрепить ревизии корпуса и FAQ, область и права, поисковые кандидаты для сравнений после поиска, модель, провайдера, промпты остальных этапов и лимит повторов. Для сквозных пар дать каждой конфигурации вести собственную историю. Для диагностики повторить один вход с одинаковой историей. Кеш использовать лишь при совпадении хеша полного запроса и параметров.
3. Для каждой гипотезы до разработки подготовить рабочие примеры и отдельный подтверждающий пакет указанного ниже размера. Из оригиналов сначала вывести проверяемый факт, зависимость и допустимый исход. Создать рядом близкий пример, где меняется ровно одно значимое обстоятельство. Все варианты одного исходного вопроса, семейства процедур или цепочки правок держать на одной стороне разделения разработки и подтверждения. Исторические Q/P/D/M/C — известная диагностика. Подтверждение строить на других ситуациях. В рантайм передавать только текст сотрудника, разрешённую историю и допустимые источники. Эталоны, тип мутации, тестовые ID и наборы обязательных шагов из `expect` доступны только оценке. Заморозить хеши до сравнения. Blind20 исключён из подготовки, настройки и исполнения.
4. Для окончательной приёмки два оценщика независимо читают перемешанные конечные ответы вместе с вопросом, историей и действующими оригиналами. По каждой просьбе фиксируют действие, видимое предписание, основание и применимость. Расхождение решают по тексту нормы, спорную интерпретацию передают владельцу. Показанный ошибочный шаг, скрытый конфликт и выпавшая предпосылка, без которой сотрудник может действовать неверно, считаются ошибочной инструкцией и в частичном ответе. Ложный отказ, лишнее уточнение и технический сбой отмечаются отдельно. При недоступности сервиса пользователь получает сообщение о сбое без инструкции.
5. На каждом наборе и маршруте показать абсолютные парные переходы и знаменатели. Главная метрика — **ходы с опубликованной неверной инструкцией / все ходы**. Дополнительно — доля ошибочных среди ходов с хотя бы одной инструкцией. Далее — **полностью пригодные ходы / все ходы**, включая оправданные уточнения и отказы, **правильно отвеченные разрешимые просьбы / все разрешимые просьбы**, **лишние предложения обратиться в качество / разрешимые просьбы**. Считать части по `requests` и фактическому тексту, поскольку общий `action=answer` возможен и при частичном ответе. Показать также целые диалоги, задержку p50/p95, число вызовов и стоимость. Рабочие и искусственные случаи показывать раздельно.
6. Общие условия допуска кандидата к следующей стадии — ни одного нового опасного показа на парных рабочих входах, сохранение 50/50 на обычных при воспроизведении контроля и прохождение своего подтверждающего пакета. Если контроль на рабочем входе оказался неверным, отдельно показать, какой ошибочный показ действительно предотвращён. Когда контроль проходит весь целевой пакет, улучшение по риску на этом пакете не доказано. Равенство по риску позволяет сравнить полезность, затем лишние эскалации. Приведённые размеры позволяют отсеять неудачную идею, но не оценить редкий промышленный риск.

## A1. Проверить обязательные шаги и их порядок до публикации

**Изменение.** Только после того, как уже выбран маршрут полной процедуры и определена её ветка, проверить общее условие и относительный порядок шагов в выбранном плане. Для ограниченного набора процедур разметить непосредственно в оригиналах связи «обязателен при условии» и «должен предшествовать», сохранить идентификатор пункта, редакцию и фрагмент-основание. Правила по редакции заранее проверяет человек без доступа к тестовым вопросам. Проверять только семантически обязательный порядок. Независимые шаги разрешено переставлять. Если в найденном контексте есть подтверждение, применить существующую одну попытку исправления и проверить результат повторно. Неразрешённая зависимость блокирует инструкцию к действию. Другие процедуры продолжают штатный маршрут.

**Сравнение.** Контроль и опыт получают одни оригиналы и один первоначальный выбор ID от C. В [`complete_ids`](../scope/procedures.py) уже есть специальные дополнения. В [дословной проверке](../scope/check_rendered_plan.py) список обязательных ID задаёт вызывающий код. Здесь проверяются только заранее описанные связи внутри уже выбранной ветки. Другие обязательства из текста не извлекаются. Заморожены выбор маршрута, применимая ветка, выдача, модель и первоначальный черновик. P01.1/P02.1 и все первые P01–P10 — диагностика. Для подтверждения взять ещё две процедуры с явной зависимостью в оригиналах, отложенные от разработки правил проверки. Для каждой подготовить шесть пар. В дефектных версиях удалить обязательное общее условие или переставить зависимые шаги. Среди корректных версий предусмотреть безопасную перестановку независимых шагов. Правила для этих оригиналов готовит другой разметчик по той же инструкции, до создания пар.

**Решение.** Всего 12 дефектных и 12 допустимых вариантов. В допустимой половине есть равнозначные порядки. Ноль опасных публикаций из 12, не менее 11/12 допустимых инструкций показаны, на P01.1 и P02.1 устранён неверный показ при его наличии в контроле. Отличать исправление, давшее полный ответ, от блокировки. Иначе снять кандидат. Дополнительных вызовов для самой проверки нет. Основная цена — разметка связей, ревизия при изменении оригинала и фактические повторы генерации. Измерить минуты разметчика на процедуру.

## A2. Выбирать применимый FAQ до выдачи конфликтующей нормы

**Изменение.** На стыке [`ApprovedFAQ.lookup`](../scope/quality.py) и [маршрута ответа](../scope/dialogue_state.py) различать исходы «применимый FAQ», «не подходит», «не хватает условия» и «два несовместимых действующих разъяснения». Сейчас отсутствие точного алиаса и несколько совпадений возвращают один `None`. В прототипе использовать прежний поиск точных алиасов и добавить поиск кандидатов по нормализованному действию и объекту. До ответа проверять источник публикации, статус, редакцию/отзыв, права и область по фактам о дирекции, операции и условиях. Недостающую область нельзя достраивать по сходству. При одном применимом разъяснении дать его со ссылкой и отметить существенное расхождение с вики. При двух равноправных несовместимых разъяснениях предложить разбор. Если сотрудник может дополнить условие — задать один вопрос. Если FAQ явно для другой ситуации — использовать действующий подходящий регламент.

**Сравнение.** Заморозить генератор, ранжирование регламентов и их снимок для каждого события. Подать обеим веткам одинаковые опубликованные снимки и действующие редакции через один интерфейс с `faq` и `faq_scope`. Обычный запуск `reasoning_trial.py` их не подключает. Рабочая диагностика — Q04/C01, текущие проверки FAQ и пример из брифа с последовательностью «качество 2 дня → вики 2 → вики 7». Проверяем первый ответ после каждой правки, включая повторное появление ранее скрытого дубля и последующий явный отзыв или замену. Обновление статусов воспроизводим готовыми снимками авторитетного сервиса. Эксперимент оценивает видимый ответ, работа по синхронизации Confluence за пределами изменения.

**Решение.** Зарезервировать 12 пар на других темах и сроках, одинаковую лексику с разной областью и парафраз с той же областью, отзыв, конфликт равных источников, устаревшую редакцию и отсутствие доступа. До прогона распределить 24 случая на 16 однозначно разрешимых и 8 требующих уточнения или предложения обратиться в качество. Ноль выдач по неприменимому источнику и недоступных цитат, не менее 15/16 верных прямых ответов, 8/8 безопасных исходов с нужным объяснением. Любой перенос FAQ за границы области отклоняет вариант. Цена — подготовка и проверка метаданных, один локальный поиск кандидатов. Без надёжного признака редакции или области на таком примере возможен только результат с явно указанным пробелом.

## A3. Проверить, что каждая просьба получила свой результат

**Изменение.** Расширить узкий случай [`verified_parts`](../scope/handoff.py) и использовать существующую [сборку по частям](../scope/conversation.py). На составном запросе планировщик возвращает интервалы символов для каждой самостоятельной просьбы, общий фрагмент условий и зависимости между частями, в том числе внутри одного предложения. Код сверяет дословные интервалы с входом и проверяет, что все вопросительные и побудительные фрагменты отнесены к части. Необъяснённый остаток помечается как нерешённый. Влияние разделения на смысл независимо проверяет оценщик. Для каждой нужны собственное действие и применимое основание либо явный пробел. Ссылки и проверенные факты общие только там, где действие, объект и условия совпадают. При независимости разрешено показать подтверждённую часть и предложить качество только по официальному неизвестному факту. При зависимости от неизвестного условия блокировать все зависящие шаги, можно сообщить безопасное общее условие. Выбор ответа, уточнения, эскалации или непрофильного отказа для выделенной части остаётся у действующего ядра. Для приёмки уточнение уместно только при нехватке обстоятельства, известного сотруднику, с максимумом в три уточнения.

**Сравнение.** Меняется только выделение частей и привязка результатов к их месту в вопросе. Заморозить поиск, генератор, судью, политику выбора действия и лимит повторов для каждой части. В первичном измерении обеим схемам передавать одинаковый сохранённый ответ на каждую дословно совпавшую часть. Далее сравнить полные прогоны и общее число вызовов. Контроль уже обрабатывает две явно отделённые просьбы и передачу ТКП. На M01–M05 и C01 проверяем сохранение смысла видимого ответа, его ссылок и правильной привязки предложения обратиться в качество. На 12 новых парах из иных процессов варьировать зависимость, удаление второй просьбы из проекта ответа, неподтверждённый срок, условие применения обеих частей и ответ в отсутствующем внешнем документе. До запуска выделить 12 случаев с независимо разрешимой частью, 6 с блокирующей зависимостью и 6 полностью разрешимых.

**Решение.** Ноль ошибочных указаний и молча потерянных существенных просьб на 24 случаях. Не менее 11/12 независимо разрешимых частей показаны с основанием, 6/6 зависимых действий удержаны до разрешения условия, 6/6 целиком разрешимых получили полный ответ. Контакт с качеством относится только к пробелу и требует подтверждения. Цена — до одного разбора на сложную реплику плюс поиск/проверка каждой отличающейся просьбы. Простые ходы должны сохранить прежний маршрут.

## A4. Проверить, к какому объекту относится продолжение

**Изменение.** После [`restore`](../scope/dialogue_state.py) проверять изменение задачи на уровне пары «операция, объект». Для местоимения, возврата к старой теме или изменения условий извлекать до двух правдоподобных объектов из реплик сотрудника и явных ссылок на шаг. Сохранять номер хода и текстовый фрагмент для каждого. Новый явно названный объект или дирекция замещает старый. Если прочтения дают разные применимые действия и сотрудник не выбрал одно, спросить, какой объект он имел в виду. Если имеется одно подтверждённое прочтение, выполнить обычный поиск по нему. Ответ бота может помочь понять явную ссылку на шаг. Основание для инструкции берётся из действующего источника.

**Сравнение.** Заморозить восстановитель Qwen и его сырой ответ для одинаковой истории, поиск, генератор C на полных процедурах и прежний судья в обеих ветках. PR #25 уже убирает лишний текст первой инструкции из обычного продолжения и возвращает пропущенную дирекцию. Здесь проверяется выбор объекта при правдоподобной, но неверной привязке. Взять P03.2/P10.2 с двумя подлинными первыми ответами, D03/D05 с возвратом и неоднозначным документом. На новых историях создать 12 пар с одинаковой последней фразой. Варьировать названный объект, доступность двух объектов, явную смену дирекции и чисто редакционную замену прежнего ответа. Заранее выделить 16 однозначных ходов и 8 с двумя различающимися основаниями.

**Решение.** Ноль уверенных ответов по чужому объекту, 8/8 содержательных уточнений на неоднозначных и минимум 15/16 пригодных ответов на однозначных. Переформулировка первой инструкции без изменения обстоятельств сохраняет действие и применимую норму. В перекрёстном опыте проверить конечный смысл P03.2/P10.2 при обеих историях. Измерить дополнительные поиски и p95 на продолжениях. Повторная генерация первой инструкции в изолированном опыте не нужна.

## A5. Остановить правдоподобный ответ независимой сверкой критического факта

**Изменение.** Взять только критические утверждения, уже написанные в черновике, например указание получателя, срока в рабочих днях или разрешения начать до оплаты. Для каждого выделить дословный фрагмент, проверяемое поле и его значение. В дословном рендере использовать позицию утверждения и его ID. Один независимый проверяющий получает исходную ситуацию, применимые оригиналы и нейтральный вопрос об этом поле. Предложенный ответ и его значение скрыты. Проверяющий возвращает значение с единицей или роль с направлением передачи, условие, точную цитату и пункт либо «не подтверждено». Код проверяет ссылку и наличие цитаты в оригинале, сравнивает типизированные значения с фактически написанными. Для отношений, которые невозможно надёжно нормализовать, правило допуска выбирают на отдельной калибровке. Разные места упоминания одной роли не взаимозаменяемы. При несовпадении или отсутствии опоры удержать черновик и передать установленную причину существующей логике исправления, уточнения или эскалации. Ошибка самого проверяющего приводит к безопасному техническому исходу.

**Сравнение.** Заморожены исходный черновик, разбиение на просьбы, история, выдача, порядок оригиналов, область и модель ответа. Единственное изменение — проверка уже написанного критического факта перед выдачей. Контроль — фактический [Decider и его пороги](../decider/policy.py) с [проверкой маршрута](../scope/ask.py), дополнительный дешёвый контроль — поднять только порог на его же ответах. Сравнить варианты при одинаковом числе допущенных правильных инструкций на калибровке. A5 не ищет пропущенные целиком шаги и просьбы. В Q04 удаление получателя диагностирует границу метода, а замена получателя на другого — целевую ошибку A5. Новый зачёт за эту знакомую пару не выставляется.

**Решение.** На других пунктах зарезервировать 24 правильных черновика и по одной минимальной ошибочной версии каждого. Поровну по шести видам ошибки — неверные роль/получатель, единица или вид дней, отрицание, условие/исключение, объект/стадия, база отсчёта срока. Сохранить правдоподобную верную ссылку и лишнее упоминание нужной роли там, где это уместно. Оба члена пары оценивать раздельно в случайном порядке. На отдельной калибровке зафиксировать правило допуска до вскрытия этих 48 исходов. Условие продолжения — 0/24 ошибочных показов, минимум 22/24 правильных допущены, число опасных пропусков ниже контроля, если контроль их допускает. Отдельно показать результат на обычных неизменённых текстах и стоимость на 100 таких проверок. Цена — до двух коротких вызовов на затронутый черновик плюс возможная одна штатная попытка исправления. Если такой же результат даёт один поднятый порог при той же полезности, дополнительный проверяющий не оправдал своей цены.

## Три дополнительных эксперимента

### K1. Сверить черновик с перечнем обязательных пунктов, составленным до чтения черновика

**Гипотеза.** Когда проверяющий сначала читает ответ, найденная им цитата может замаскировать то, чего в ответе вообще нет. На Q04 Decider нашёл точную строку, но пропустил удаление получателя ТКП.

**Вариант.** В одном независимом вызове передать только вопрос, подтверждённые условия и собранные оригиналы. Попросить указать для каждой просьбы, какие обязательные действия, роли, условия и зависимости следует отразить. Для каждого требования вернуть дословный фрагмент и допустимые ID утверждений из текущего входа. В экспериментальном перехватчике `evidence.generate` сохранить итоговую последовательность ID после действующего дополнения выбора и перед рендером. Код сверяет фрагменты с оригиналами, применимость с известным контекстом, наличие обязательного утверждения или одного из равноценных и порядок зависимых шагов в черновике. Невалидный план или пробел переводит соответствующую часть в штатное уточнение или предложение обратиться в качество. Для сравнения использовать только ответы, собранные из существующих утверждений.

**Контроль и проверка.** Заморозить проверенные черновики и источники. Сравнить действующий допуск с тем же допуском плюс независимая сверка. Взять Q04, P01.1, P02.1, P08.1, P10.2 и минимум один ответ с несколькими допустимыми способами формулировки. Для каждой пары изменить только одно утверждение или его место: удалить обязательный ID, заменить его похожим ID из тех же доступных источников или поменять порядок. Сохранить вопрос, первый вход и редакции документов. Успех — остановлен хотя бы один дополнительный опасный черновик, пропущены все заранее размеченные полные ответы в панели и ни один испорченный вариант, меняющий решение сотрудника. Цена — один модельный вызов на проверяемый ответ. На живом маршруте сначала измерить стоимость на процедурах и составных запросах.

### K2. Выбрать следующее действие по причине пробела

**Гипотеза.** Число лишних обращений можно снизить, если отличать неизвестный факт о проекте, который знает сотрудник, от отсутствующего нормативного сведения. В `scoped_result` оценка `needed_fact` сейчас влияет на специальный маршрут `requested_fact`. Составная реплика может также содержать полностью подтверждённую просьбу.

**Вариант.** На замороженных источниках и черновиках сравнить штатное действие с классификацией каждой незакрытой просьбы. Разбиение фиксировано и совпадает между вариантами. Если действующий маршрут вернул одну просьбу, на живой проверке она остаётся одной. На специально выделенных парах можно сравнить классификатор с заранее зафиксированным одинаковым разбиением. Для уточнения потребовать одно поле, значение которого может сообщить сотрудник и две подтверждённые оригиналами ветви, в которых от его значения меняется действие. Если факт уже назван в истории или все подтверждённые ветви дают один результат, уточнение убирается. Если требуемое правило, срок или реквизит должен подтвердить владелец процесса, предложить передачу в качество по этой части. Подтверждённые части показать, если ими можно воспользоваться самостоятельно. Действующие правила для вариантов по нескольким дирекциям и лимита уточнений сохраняются. Непрофильную часть обработать штатным ответом о границах сервиса. Сохранить текущую проверку прямого ответа и подтверждение отправки сотрудником.

**Контроль и проверка.** Зафиксировать одинаковые черновики и выдачу. Сравнивать только выбор действия, формулировку уточнения и объём эскалации. Взять D01, D02, D05.3, M02, M03, M04, C01 и пары, где добавляется ровно один разрешающий факт либо ровно одна самостоятельная просьба без основания. Успех — хотя бы два улучшенных выбора действия или объёма обращения, сохранены все корректные ответы на контрольной панели, нет новых неподтверждённых инструкций. На первом проходе решить задачу одной пакетной проверкой по всем частям и замерить её цену.

### K3. Повторить поиск по одному выявленному пробелу

**Гипотеза.** Повтор по исходному вопросу часто возвращает похожие фрагменты. Запрос о конкретном недостающем условии может вернуть нужный пункт без общего расширения контекста. Такой повтор полезен, только когда исходная выдача действительно не содержит основания.

**Вариант.** На штатном маршруте `retrieve` после первого черновика за один короткий модельный вызов описать конкретный пробел и предложить подзапрос. Вход — вопрос, первый черновик, его проверка и уже найденные фрагменты. Подзапрос включает известные дирекцию, объект, этап и запрошенный реквизит. Код отвергает добавленные предположения о дирекции и числовых значениях. Пропустить подзапрос через действующие BM25 + MiniLM, добавить до пяти новых оригинальных пунктов с проверкой редакции и применимости. Число попыток генерации и финальная проверка прежние. Если проверяющий увидел нужный пункт в первом входе, направить на исправление черновика. При неизвестном факте о проекте срабатывает уточнение. При отсутствии подтверждения после повтора — предложение обратиться в качество по пробелу.

**Контроль и проверка.** Заморозить первый вход, черновик и причину повтора. Сравнить штатное расширение выдачи и целевой подзапрос при одинаковом бюджете до пяти новых оригиналов. Сохранить отдельно результат исходного маршрута с его штатным лимитом. Проверить на тех рабочих трассах, где действительно отсутствует эталонный пункт. Добавить контролируемое удаление нужного фрагмента из первого входа и парный вариант, где он уже присутствует. Включить один пробел без ответа в корпусе и один соседний пункт из неприменимой дирекции. Успех — восстановлены минимум два нужных пункта и хотя бы один ранее потерянный ответ, случаев публикации неприменимой инструкции не прибавилось. Цена — не более одного дополнительного поиска и одного короткого вызова на запрос, отправленный на повторную выдачу. Модель и лимит повторов генерации прежние.

## Порядок ночной проверки

1. **Воспроизвести контроль.** Сохранить собственные результаты контрольного ядра. Сначала проверить доступ к моделям, рабочему пакету и MiniLM. Если первые реальные ответы доступны, выполнить два перекрёстных сравнения P03/P10 по [инструкции](reasoning-results.md). После первого воспроизводимого замера можно начать целевые панели.
2. **Запустить все восемь отдельно.** Начать с A1, A5 и K1 на замороженных черновиках. A2 можно проверить независимо на снимках FAQ. Затем A3, A4 и K2 на их целевых сценариях, K3 на сохранённых входах повторного поиска. Каждый вариант включать одним переключателем. Использовать отдельные каталоги. Хешировать полные запросы при повторном использовании вызовов. Не объединять изменения до замера.
3. **Сравнить до двух лидеров на 42 + 50.** Использовать их собственную фактическую историю. Для рекомендации к публикации нужен ноль критических ошибок на пройденных панелях и полном прогоне. Сначала сравнить неверные инструкции, затем правильно решённые вопросы и лишние эскалации. Если этап блокируется отсутствующими данными, завершить доступные панели и указать, какая проверка не выполнена.
4. **Закоммитить отчёт.** Для каждой гипотезы указать SHA и команду, число выполненных примеров, ошибки, дельты, изменившиеся рабочие ходы, первый этап расхождения, задержку и стоимость. Автоматический результат по маршруту, ID, известным мутациям и ссылкам отделить от оценки смысла по оригиналам. Там, где нужна проверка человеком, подготовить материал для утренней сверки. Исходные закрытые вопросы, ключи и полные трассы остаются в окружении.
