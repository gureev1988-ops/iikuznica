## Общее правило FAQ

Оба кандидата сначала отвечают по применимому регламенту. Разъяснение добавляется после проверки нормативного ответа. При доказанном совпадении показываем оба источника. При расхождении добавляем позицию FAQ со своей ссылкой, явно указываем приоритет регламента и предлагаем повторное уточнение. При незавершённой проверке сохраняем приоритет регламента и сообщаем, что сопоставление требует проверки. FAQ закрывает пробел только как консультация, когда пробел подтверждён. [Требования к приложению и почтовому пути в PR #33](https://github.com/gureev1988-ops/iikuznica/pull/33)

Раннер использует пустой снимок FAQ, если оператор не передал авторизованный и зафиксированный снимок через `--faq-snapshot` и `--faq-scope`. Для снимка используется список записей в формате `ApprovedFAQ` с полем `comparison.status`. Значения — `match`, `conflict`, `gap` или `pending`. Для первых двух нужен `comparison.basis` с `doc`, `ref` и точной `quote` из действующего корпуса. Снимок и область входят в манифест. Во всех режимах отдельно проверяем общую логику приоритета на воспроизводимых примерах.

Этот раннер проверяет ответы поискового ядра. Почтовый цикл, очередь «Возможное противоречие», правку, отзыв и одинаковое поведение на вебе и в DION проверяет сквозная приёмка приложения из PR #33 после реализации бэкенда.

## Запуск в Codex Cloud

Зафиксируй SHA ветки прогона. Укажи оригинальные архивы и среду с прежними MiniLM, Python, зависимостями поиска и `OPENROUTER_API_KEY`. Для нового набора принимается как проектный `IIkuznitsa_Final_Control20.zip`, так и входной `IIkuznitsa_Final_Control20_Inputs.zip`. Из проектного пакета считывается только вложенный архив входов. Для исходного Blind20 передай `IIkuznitsa_Blind20_Inputs.zip`.

```bash
D=/workspace/scratch/answer-quality-pr26
T=eval/conversations/final_compare.py
ARGS=(
  --working50 "${WORKING_ZIP}"
  --blind20 "${BLIND20_INPUTS}"
  --final-control20 "${FINAL_CONTROL20}"
  --model-dir "$D/minilm"
  --python "$D/venv/bin/python"
)
python3 "$T" "${ARGS[@]}" --check
python3 "$T" "${ARGS[@]}" --out "$D/final-comparison"
```

Команда проходит все четыре набора последовательно. По умолчанию второй кандидат переиспользует только полностью совпавшие запросы A1 внутри этого прогона. Повтор с тем же каталогом продолжает с точных сохранённых вызовов. Для сопоставимой холодной задержки используй новый каталог и `--independent-calls`.

В `manifest.json` фиксируются SHA кода, корпуса, наборов, снимка FAQ и настройки моделей. В `summary.json` лежат агрегаты и число ходов. Для рабочих наборов сохраняется `pairs.json`. Для каждого закрытого набора проверяющему передаётся только `review.json` с перемешанными ответами. `private-arm-map.json` открывается после фиксации оценок. В Git достаточно агрегатов и итогового отчёта.

## Выбор победителя

1. На всех четырёх наборах фиксируем критические ошибки. Сюда входят уверенная ошибочная инструкция, неприменимое обязательное условие, выдуманный источник и инструкция по FAQ в конфликте с действующим регламентом. Отдельно проверяем известные защитные блокировки и 5/5 контрольных условий.
2. При сопоставимой безопасности сравниваем пригодность целых ответов. Приоритет у нового Final Control20, где зафиксирован порог 19/20. Указываем результат по простым 5 и сложным 15 отдельно. Затем сверяем исходный Blind20 и рабочие 42 + 50. Пропущенные подтверждённые части, лишние уточнения и эскалации считаем отдельно.
3. При равном качестве сравниваем число вызовов и сопоставимую задержку. При парном кеше время хода выводится как диагностическое. Если ни один кандидат не достиг порога, в отчёте отдельно фиксируем, какой вариант сильнее и какие условия приёмки остались открыты.
