# Процедуры и диалоги в одной ленте

Рабочее дополнение к банку из 50 вопросов. Здесь 21 сценарий и 42 реплики сотрудника. Набор предназначен для разработки. Отложенная проверка на 20 новых вопросах остаётся отдельной.

| Файл | Состав | Что проверяем |
|---|---|---|
| [procedures.jsonl](procedures.jsonl) | 10 процедур, по два хода | На первом ходу сотрудник просит провести его по процессу. На втором меняет условие или ссылается на предыдущий ответ. Для каждого хода записаны обязательные сведения и пункты оригинала. |
| [dialogues.jsonl](dialogues.jsonl) | 5 разговоров, 16 ходов | Ответ на уточнение, смена темы в ожидании уточнения, продолжение после ответа, возврат через другую тему, неоднозначная ссылка на документ. |
| [compound.jsonl](compound.jsonl) | 5 пар независимых просьб и один вопрос по нескольким аспектам одной процедуры | Два ответа, ответ с уточнением, ответ с пробелом в данных, вопрос про зарплату рядом с профильным. Нужен отдельный результат по каждой просьбе. |

В десятке процедур есть согласование договора с заказчиком и допуск субподрядчика в Технической дирекции, ранний старт и оформление УПД в ДБРЦТ, регистрация сайта и сдача работ в ИБ, выбор предложения и поиск субподрядчика на пресейле ИБ, управление изменениями в ДБРЦТ и архивирование в Технической дирекции. Эталоны составлены по четырём DOCX. «Бриф» как обязательный этап подписания договора в Технической дирекции в эталон не включён.

## Первый замер на ядре 9b7b3f1

Для первого хода каждой процедуры воспроизведены BM25, MiniLM и фактическое расширение источников до передачи генератору. Эксперимент дополнительно берёт до восьми пунктов из каждого из двух разделов, чаще всего встречающихся среди пяти лучших результатов. Метрика засчитывает процедуру только при наличии всех обязательных ссылок. Знание эталона при выборе раздела исключено.

| Доступные генератору пункты | Все опорные пункты найдены | Медиана количества пунктов |
|---|---:|---:|
| Первая пятёрка после переранжирования | 2/10 | 5 |
| Действующее расширение ядра | 6/10 | 11 |
| Дополнительно раскрыть два раздела | 9/10 | 18 |

Для процесса поиска субподрядчика по-прежнему упущен пресейл ИБ §10.2 о роли ресурс-менеджера. Покрытие источников ещё предстоит сопоставить с полнотой и скоростью ответа.

Для десяти заведомых продолжений отдельно сравнили первую пятёрку поиска. Изолированная реплика дала все нужные ссылки в 6/10, добавление всего предыдущего вопроса — в 7/10. Появились нужные пункты для объявления победителя и возврата проекта из архивирования (P05 и P06), но исчез пункт о расчёте стоимости изменения (P08). Поэтому проверяем восстановление только нужного предмета и дирекции с сохранением акцента последнего вопроса.

В проверке передачи истории использованы заданные предыдущие ходы и признак того, задал ли бот вопрос. Все десять продолжений после утвердительного ответа ушли в поиск без предыдущей темы. В D02 самостоятельный вопрос о просрочке во время уточнения о встрече получил встречное «Встреча внутренняя или с заказчиком?». В M02 ранняя эскалация по размеру файла поглотила вопрос об УПД. В M04 дирекция второй просьбы попала в первую, а вопрос по УПД остался без ответа. M05 предлагает запрос только по размеру файла и оставляет личную просьбу без реакции. Эти результаты получены до обращения к модели. Они не измеряют качество всех финальных реплик.

## Как оценивать ответ

1. Для процедуры отметить по каждому шагу действие, исполнителя, условия, срок, если он задан, и подтверждающую ссылку. Засчитывать равнозначную формулировку. Проверить зависимости по порядку действий. Параллельные шаги допускают разный порядок, условные ветви должны быть явно названы. Перечисление возможных форматов приёмки как обязательных последовательных этапов — ошибка.
2. Для диалога сравнить продолжение с исходной темой, дирекцией и последней репликой бота. При смене темы проверить, не перенеслись ли ограничения старой. При двух правдоподобных ссылках уместен короткий уточняющий вопрос. Живой прогон использует собственные предыдущие ответы. Первый сбой отмечать отдельно от его последствий.
3. Для составного сообщения оценить каждую просьбу. Прямой ответ и его цитата могут соседствовать с уточнением или адресным предложением обращения. Письмо отправляется только после согласия на конкретный вопрос. Общий балл за ход — только если все части пригодны, за диалог — только если пригодны все его ходы. Проверять факты по оригиналам даже при правильном выборе маршрута.

Ближайший кандидат для сравнения хранит в диалоге активную тему, подтверждённые обстоятельства, открытый вопрос бота и ссылки на недавние темы. Для каждой новой просьбы выбирает нужный контекст. После разделения независимых просьб поиск и решение об обращении выполняются по каждой отдельно. В рамках одной процедуры сохраняются условия ветвления и последовательность шагов.

## Воспроизведение

Офлайн-проверка работает на включённом снимке реальной выдачи. Снимок содержит ссылки на пункты, оценки и хеши поисковых запросов, без эталонных ответов.

```sh
python3 eval/conversations/check.py probe --out /tmp/conversation-probe.json
```

Полный прогон базового ядра в окружении с OpenRouter. Каждый сценарий начинается с пустой историей. Реплики одного сценария исполняются последовательно, кеш сохраняет успешные вызовы по содержимому запроса. В `replies.jsonl` сохраняется текст для сверки с оригиналами.

```sh
python3 eval/conversations/check.py live --out /tmp/conversation-baseline
```

[Сквозной результат исходного ядра](baseline.md) — 19 из 42 пригодных ходов. Для пяти независимых пар предусмотрен контрольный опыт. В нём заранее известно, что просьбы независимы. Разрезаем исходное сообщение между двумя явными вопросами, убираем вводную связку и отправляем обе части тому же ядру с пустой историей. Успех пары требует двух пригодных реплик и предложения обратиться в качество только там, где это требуется. Этот опыт измеряет эффект раздельной обработки, распознавание границы в произвольной речи и объединение ответа сотруднику проверяются отдельно.

```sh
python3 eval/conversations/check.py live --independent-parts --out /tmp/conversation-independent-parts
```

Для обновления снимка установить зависимости в `eval/retrieval` командой `npm ci` и использовать модель и Python из [инструкции MiniLM](../rerank/README.md). Добавление новых вариантов поиска требует пересборки снимка.

```sh
python3 eval/conversations/check.py prepare --model-dir "$MINILM_DIR" --python "$RERANK_PYTHON"
```

## Разбор сообщения и истории

Эксперимент включается флагом `--conversation` у `eval/scope/ask.py`. Можно передать `--history-file` с историей пользователя и реальными ответами ассистента. Ядро возвращает общий текст с пронумерованными источниками и поле `requests` с отдельным действием по каждой просьбе. Если запросов в службу качества несколько, при подтверждении передаётся индекс выбранной части.

Живой прогон использует подключение к OpenRouter и локальный MiniLM с проверкой контрольных сумм. Поиск выполняется по уточнённому тексту после выбора темы. Две команды используют разные каталоги для ответов и кеша.

```sh
python3 eval/conversations/check.py candidate --model-dir "$MINILM_DIR" --python "$RERANK_PYTHON" --out /tmp/auto42
python3 eval/conversations/check.py candidate --working50 "$WORKING50_ZIP" --model-dir "$MINILM_DIR" --python "$RERANK_PYTHON" --out /tmp/auto50
```

При раздельном размещении генератора и поиска флаг `--defer-search` сохраняет недостающие запросы в `pending.json`. Команда `rank-pending` рассчитывает для них выдачу тем же MiniLM. Повторный `candidate` с тем же каталогом результатов и `--extra-cache` продолжает обработку. Сырые вопросы, ответы и выдачу по закрытым наборам следует хранить в согласованном окружении.

Для отдельной проверки явных независимых просьб у команд `ask.py` и `check.py candidate` есть флаг `--explicit-pair`. Он разделяет два полных вопроса в первом сообщении, если вторая просьба явно задаёт дирекцию или является самостоятельным личным вопросом. При зависимой формулировке и в последующих ходах работает исходное ядро. [Результаты сравнения](candidate-review.md)

## Состояние темы в многоходовом диалоге

Маршрут `--state-model` сохраняет основной генератор и судью. Модель с указанным ID получает только задачу связать новый ход с одним из предыдущих или задать вопрос о неоднозначной ссылке. Состояние для обращения к ядру хранит вызывающая сторона в границах одного диалога. В записи есть исходная реплика `user`, фактический ответ `assistant`, действие `action` и самодостаточный вопрос `resolved`, полученный из `resolved_question` предыдущего ответа. В следующем запросе источниками снова служат действующие документы и применимый FAQ службы качества. Короткий ответ на конкретный вопрос о дирекции или виде встречи обрабатывается по полям уже начатой темы.

Для повтора сквозного эксперимента запусти команду отдельно для двух ID модели и укажи разные выходные каталоги. Результаты 50 одиночных запросов проверяются тем же маршрутом с `--working50`. Повторно используются только запросы с совпадающими входами и моделью.

```sh
python3 eval/conversations/check.py candidate --state-model "$RESOLVER_MODEL" --model-dir "$MINILM_DIR" --python "$RERANK_PYTHON" --out "$RESULT_DIR"
```

В этом варианте отдельно проверяется передача ТКП при явном отказе заказчика ИБ от услуг. Прямой ответ подтверждается дословной строкой применимого пункта в текущей выдаче. Для дополнительного вопроса о сроке запускается отдельный поиск. Результат по каждому подтверждённому факту сохраняется при предложении обратиться в качество по остающемуся пробелу. Правило охватывает одну проверенную ветвь процесса.
