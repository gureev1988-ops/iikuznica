# Подключение внутренних моделей

Профиль пилота использует три готовые внутренние точки HTTP(S) и локальные файлы MiniLM. API и оба воркера получают одинаковую карту ролей. Команды ниже выполняются из корня репозитория на Linux с Docker Compose v2. Для запуска сервисов моделей на отдельном GPU-узле см. [инструкцию для GPU-узла](../../deploy/local-inference/README.md).

## Подготовка

1. Получите у ИТ полные адреса POST, идентификаторы обслуживаемых моделей и при необходимости отдельный Bearer-токен для каждой роли. Адреса должны быть доступны **из контейнеров приложения**. Если GPU стоит на отдельном узле, укажите внутреннее DNS-имя этого узла или корпоративного шлюза. В примере GPU-сборки Gemma, Qwen и Decider публикуются на портах 18081, 18082 и 18083. ИТ задают приватный адрес привязки и доступ с узла приложения.
2. Для Gemma и Qwen укажите путь `/v1/chat/completions`. Оба сервиса должны поддерживать SSE, поток с `finish_reason: stop`, завершающее событие `[DONE]` и выдачу статистики токенов при наличии. Для Qwen используйте серверный чат-шаблон с выключенным thinking для применяемого режима. Для Decider укажите нативную точку `/v1/decisions`, которая принимает `model`, `state` и `questions` и возвращает решения по запрошенным ключам, включая вероятности вариантов. Подробности форматов описаны в [контракте коннекторов](../architecture/llm-connectors-v1.md).
3. Из внутреннего хранилища подготовьте каталог на узле Docker с двумя файлами ниже. Обоим файлам требуется доступ на чтение для UID 10001, а родительским каталогам — доступ на проход. Compose монтирует каталог в `/models` в режиме чтения для `init`, `api`, `interactive` и `background`. При инициализации проверяются SHA-256 и загрузка модели на CPU.

| Файл из `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`, ревизия `1427fd652930e4ba29e8149678df786c240d8825` | Имя в каталоге на узле | SHA-256 |
| --- | --- | --- |
| `tokenizer.json` | `tokenizer.json` | `62c24cdc13d4c9952d63718d6c9fa4c287974249e16b7ade6d5a85e7bbb75626` |
| `onnx/model_qint8_arm64.onnx` | `model_qint8_arm64.onnx` | `1825907d6c1a9001ff78124780bbde20a614a8c3df3b63409cf3c72c6fe5c8b4` |

Если комплект MiniLM ещё нужно подготовить для внутреннего хранилища, на машине с разрешённым доступом к Hugging Face выполните следующие команды. Перенесите полученные два файла в каталог `II_MINILM_HOST_DIR` на узле приложения.

```sh
minilm_src=https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1/resolve/1427fd652930e4ba29e8149678df786c240d8825
mkdir -p .ii-local/minilm
curl --fail --location "$minilm_src/tokenizer.json" -o .ii-local/minilm/tokenizer.json
curl --fail --location "$minilm_src/onnx/model_qint8_arm64.onnx" -o .ii-local/minilm/model_qint8_arm64.onnx
```

## Настройка и запуск

При первом развёртывании создайте пароли БД и почты и рабочую копию примера. Для действующего проекта используйте его существующий файл `.env`.

```sh
./deploy/init-env.sh
mkdir -p -m 700 .ii-local
install -m 600 deploy/models/local.env.example .ii-local/models.env
```

В `.ii-local/models.env` укажите абсолютный путь `II_MINILM_HOST_DIR` и заполните три пары `URL` и `MODEL`. `TOKEN` для каждой роли можно оставить пустым при отсутствии аутентификации. Для внутреннего HTTPS из собственного центра сертификации положите доверенный PEM-bundle в подготовленный каталог и задайте `II_LOCAL_CA_FILE=/models/pilot-ca.pem`. По умолчанию используется системное хранилище образа. Запрос к модели выполняется напрямую с проверкой TLS. Для пилота ограничьте исходящую сеть приложения разрешёнными внутренними сервисами на уровне инфраструктуры.

Команда `pilot` ниже закрепляет отдельное имя проекта и явно выбирает локальный профиль. Для обновления уже развёрнутого пилота используйте имя его существующего Compose-проекта, чтобы подключить его тома. Проверка `config --quiet` не печатает пароли и токены.

```sh
pilot() {
  docker compose --project-name iikuznica-pilot \
    --env-file .env --env-file .ii-local/models.env \
    -f compose.yaml -f deploy/models/compose.local.yaml "$@"
}
pilot config --quiet
pilot build api imap
pilot run --rm --no-deps --entrypoint python api -m backend.assembly.check_models
pilot up -d --wait
pilot ps --all
```

Команда проверки посылает синтетические запросы каждой роли из окружения приложения. Проверяйте после загрузки весов и прогрева серверов. Для допуска пользователей все три роли должны вернуть `ok` в пределах сроков приложения. В каждой строке сверьте адрес, настроенную и фактическую модель. Если сервис не вернул идентификатор, команда покажет `unverified` и ненулевой код завершения. При ошибке проверьте эти же адреса, имена, CA и токены и повторите команду. После запуска откройте DION, проверьте вопрос с цитатой, уточнение и согласованный почтовый цикл. Для выпуска сохраните SHA приложения, digest образов и версии весов, результат проверки подключений и сценариев на этом комплекте.

## Переключение и откат

Перед изменением рабочего подключения сохраните защищённую копию файла параметров проверенного профиля.

```sh
install -m 600 .ii-local/models.env .ii-local/models.env.last-good
```

Внесите изменения в `.ii-local/models.env`, выполните `pilot config --quiet` и повторите `pilot run --rm --no-deps --entrypoint python api -m backend.assembly.check_models`. Текущие процессы продолжают работать до `pilot up -d --wait`. Для отката верните проверенный файл и повторите приёмку.

```sh
install -m 600 .ii-local/models.env.last-good .ii-local/models.env
pilot config --quiet
pilot run --rm --no-deps --entrypoint python api -m backend.assembly.check_models
pilot up -d --wait
```

При откате версии приложения используйте соответствующий проверенный образ и порядок восстановления БД из [инструкции эксплуатации](assembly-run.md). При переключении подключений в пределах одного проекта PostgreSQL, оригиналы и почта продолжают использовать прежние тома. Публичный демостенд развёртывается своим [профилем VPS](vps-deploy.md).
