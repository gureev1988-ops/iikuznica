# Базовая обвязка бэкенда — контракт для планирования v0.3.1

Эта публичная редакция описывает границы поставки, интерфейсы и исполняемые проверки. На её основе можно разбить работу на пакеты, разработать адаптеры и выполнить контрактный прогон на синтетических данных. Окончательный выбор движка поиска и оформление веб-клиента относятся к последующим этапам.

## Состав первого выпуска

Один Python-бэкенд на FastAPI, клиентский контракт для TypeScript и PostgreSQL. Три режима запуска одного приложения: HTTP API, интерактивный воркер и фоновый воркер. Интерактивный воркер держит движок прогретым. Фоновый обслуживает интеграции, доставку, синхронизацию и повторы. Веб, чат-адаптер и фон вызывают общие прикладные команды. Параметры подключений передаются конфигурацией. Локальный запуск использует синтетические источники и почтовый имитатор.

| Пакет | Результат |
|---|---|
| Контракты и хранение | OpenAPI v1, типы TypeScript, доменные ID, миграции, версионные источники, история и ограничения уникальности |
| Диалоги | Приём сообщения, уточнение, предложение действия и подтверждение, проверяемые ссылки на источники, восстановление после обрыва |
| Исполнение и модель | Устойчивая очередь, ограничение параллелизма, журнал физических вызовов, восстановление и сверка неопределённых исходов |
| Документы | Порт источника документов, пакетный импорт, адаптер штатного REST API self-hosted Confluence, версии и курсор синхронизации |
| Почта и FAQ | Исходящее обращение, корреляция ответа, запись знания, обратная доставка, постмодерация и отзыв |
| Чат-адаптер | DION Bot API v2, обработка событий личной ленты, текстовые подтверждения и обратная доставка |
| Приёмка | Миграции на чистой БД, контрактные и интеграционные проверки, сквозные сценарии, замеры нагрузки и восстановления |

## Граница ядра и клиента

Порт `AnswerEngine v1` принимает вопрос, идентификаторы хода и обращения, подтверждённые условия, историю данного обращения, дедлайн и доступ на чтение к разрешённому снимку источников. Движок сам выбирает и ранжирует источники. Возвращает действие `answer | clarify | escalate | out_of_scope`, текст, варианты уточнения и основания каждого существенного тезиса: ID документа, редакции, фрагмента и дословная выдержка. Сетевой отказ имеет отдельный технический исход. Обвязка проверяет области действия и ссылки, назначает ID действий, формирует URL и записывает историю. Побочные эффекты выполняются только прикладным слоем. Для разработки достаточно детерминированной реализации порта и версионных фикстур.

Общие опубликованные FAQ доступны из PostgreSQL сразу после фиксации. При однозначном совпадении вопроса и условий применимое официальное разъяснение имеет приоритет над расходящимся документом даже при остановленной фоновой индексации или недоступной модели. Ответ с расходящимся источником содержит пометку. Архивирование дублирующей выдачи связывается с конкретной покрывающей редакцией документа. Новая редакция, утратившая эквивалентность, снова даёт приоритет действующему FAQ. Явный отзыв или замена снимает прежнее основание для новых ответов. Существующая история сохраняет версию, процитированную в момент ответа.

## Поверхность API

| Команда | Контракт |
|---|---|
| `POST /v1/conversations/{id}/messages` | Стабильный ID клиента. Реплика и задание фиксируются вместе. Ответ `202` содержит `conversation_id`, `case_id`, `turn_id`. Для продолжения передаются ID уточнения и выбранного варианта либо свободный текст |
| `GET /v1/conversations/{id}/messages`, `GET /v1/turns/{id}` | История, состояние хода, источники, открытые уточнения и предложения с ID и версией. Снимок содержит согласованный курсор событий |
| `GET /v1/conversations/{id}/events` | SSE с возобновлением по `Last-Event-ID`. Истёкший курсор восстанавливается чтением снимка. События привязаны к ленте, кейсу и, где применимо, ходу |
| `POST /v1/offers/{id}/confirm` и `/decline` | Действие владельца по открытой версии предложения. Подтверждение создаёт единственный исходящий эффект |
| `POST /v1/turns/{id}/retry` | Идемпотентный повтор технически неуспешного хода в том же кейсе |
| `GET /v1/sources/{revision_id}/fragments/{id}` | Исторический или текущий фрагмент после проверки права просмотра |
| Команды качества | Очередь ожидающих обращений, ручная привязка технически неопознанного письма, разбор расхождений, отзыв/замена FAQ с контролем версии. Ответ сотрудника на встречный вопрос возвращается в ту же почтовую цепочку |
| Технические операции | Состояние подключений, ручная синхронизация и её результат, очередь и причины ошибок, журнал расходов. Административные команды доступны соответствующей роли |

У веб-клиента и чат-адаптера одинаковые сценарии и разные представления. Совместимые изменения API добавляют необязательные поля. В сценариях проверяются переключение движка и откат, в том числе при открытом уточнении или предложении отправки.

## Адаптеры и данные

- **Документы.** Читать согласованные источники постранично, сохранять неизменяемый снимок, идентификатор внешней страницы, версию, структуру пунктов и якоря. Индексация предшествует атомарной активации новой применимой редакции. Контрольный проход сверяет перемещение, удаление, архив и потерю доступности. Обрыв на середине списка не должен убрать оставшиеся страницы. Повторный импорт той же версии безопасен. Отдельно проверяется чтение двух версий страницы в установленном профиле API.
- **Почта.** После согласия пользователя письмо отправляет бот на настроенный общий адрес с сотрудником в копии. Обычный Reply должен вернуться в наблюдаемый ящик. Приём проверяет происхождение от настроенного доверенного ящика и связывает письмо с исходным кейсом по заголовкам цепочки либо проверяемому идентификатору. Содержательный ответ сразу становится FAQ без ручного допуска, а автор исходного вопроса получает уведомление в своей ленте. Общая выдержка и сырое письмо имеют отдельные права. Автоответ, отказ доставки и просьба уточнить — самостоятельные события. Смешанный ответ публикует уже разрешённую часть и сохраняет ожидание по остальной. Техническая привязка ранее неопознанного письма возобновляет тот же процесс. Учесть повтор сообщения, исправление, отзыв, повторное чтение почты после сброса курсора.
- **DION.** Один личный чат может содержать несколько кейсов. Использовать штатные авторизацию, long polling и отправку сообщений. Адаптер хранит курсор и входы совместно, дедуплицирует события, сохраняет точность 64-битных ID и обрабатывает истечение токена и асинхронную ошибку отправки. Входы ленты маршрутизируются последовательно до запуска работ по кейсам. Текстовое согласие относится к одному предложению. При неоднозначности бот уточняет адресата действия. Поздний ответ содержит ссылку на исходное обращение.
- **Права.** Роль сотрудника даёт чтение общего корпуса. Личные ленты, исходная переписка, постмодерация и технические операции проверяются отдельно. Повторно проверить доступ и актуальность основания перед выдачей, открытием источника и отложенной доставкой. Публичные тестовые данные полностью синтетические.

## Исполнение и диагностика

Сохранять в PostgreSQL кейсы, реплики, согласия, события, обращения, источники и их версии, FAQ, входящие квитанции, задания, исходящие попытки и вызовы моделей. Большие исходные файлы допускается хранить на постоянном томе или в приватном объектном хранилище с идентификатором и контрольной суммой. Повторяемые операции имеют уникальные бизнес-ключи. Курсор, запись сообщения и постановка дальнейших действий фиксируются атомарно там, где потеря одного из них оставила бы запрос без ответа.

Воркер получает задание с ограниченной по времени арендой и токеном владельца. Сетевые вызовы выполняются за пределами транзакции. Для SMTP и чат-доставки попытку `sending` нужно зафиксировать до I/O. При сбое после возможного приёма поставщиком — `delivery_unknown` и сверка. Слепой повтор может создать второе письмо или сообщение. Лимиты, дедлайны, повторы с задержкой и отказ до приёма задаются отдельно для интерактивной и фоновой работы. Каждый принятый ход должен иметь один сохранённый результат или явный технический итог.

На каждую физическую попытку вызова модели сохранять роль вызова, `trace_id`, модель и фактический маршрут, время, статус, входные и выходные токены и доступные сведения о списании. Учитывать повторы и вызовы судьи. Неизвестная стоимость хранится отдельно от нулевой. Выгрузка агрегирует по ходу и обращению и отдельно выделяет фоновую обработку. Замерять ожидание очереди, первое полезное событие, полный проверенный ответ и время ожидания человека. Состояние БД и готовность API отделены от состояния опциональных интеграций.

## Приёмка на синтетических данных

1. Два взаимозаменяемых движка проходят один набор сценариев. Переподключившийся клиент восстанавливает открытое согласие, уточнение, версионную ссылку и поздний ответ.
2. Двойное подтверждение создаёт одно письмо. После рестарта ответ возвращается в исходную ленту. Сразу после получения официального ответа второй сотрудник получает применимый FAQ, в том числе при остановленных индексации и постмодерации.
3. Учебный пример для поиска: FAQ устанавливает срок 2 дня; редакция A документа тоже даёт 2; редакция B меняет срок на 7. Приоритет разбора возникшего расхождения — наивысший. До явного отзыва или замены сотрудник получает 2 со ссылкой на FAQ и пометкой о расхождении.
4. Проверить технический сбой модели, таймаут почтового сервера, перезапуск до и после внешнего принятия, отказ затем согласие по одному предложению, дубликаты входов и гонку ответа с отзывом источника. Подтверждённое содержимое не должно теряться или повторно отправляться без установленного результата предыдущей отправки.
5. В базовом тесте принять все 10 одновременных валидных ходов. При 20 и 200 измерять явное ограничение приёма, итог каждого принятого хода и восстановление. Ориентиры измерения при 10 — p95 до 5 секунд до содержательного события, до 15 секунд до полного ответа. Результаты имитатора и фактические замеры на стенде указываются раздельно.
6. Проверить восстановление БД и снимков документов вместе. Статус контрактных тестов каждого адаптера и результат живого прогона фиксируются отдельно. Для почтовой приёмки провести полный обмен между тестовыми ящиками; для остальных внешних подключений живой прогон требует предоставленного доступа.

## Правила работы с Git

Планировщик запускается Кириллом. Каждый самостоятельный пакет получает отдельную ветку, изолированную рабочую копию и свой PR. Исполнитель пушит только в свою ветку. Прямые изменения и автоматическое слияние в `main` исключены. Параллельные ветки поиска и дизайна принадлежат их исполнителям. Перед сдачей сверься с актуальным `main`, сохрани изменения соседних команд и повтори затронутые проверки. У зависимых PR укажи базу и порядок интеграции. В описании каждого PR — границы пакета, проверки, результаты и оставшиеся внешние зависимости. Слияние выполняется отдельно после ревью.
