# Дополнительные документные источники · v1

**Задание на реализацию для Codex.** Цель хакатона — подключить две независимые документные выгрузки через конфигурацию, обновлять их по расписанию и проверять каждую по отдельности. Первая реализация принимает полный каталог HTTPS/JSON. Принимаем результат по автоматическим тестам и письменной инструкции. На показе используется прежний локальный корпус.

**Исходная точка.** Сверено с [интеграционной веткой бэкенда на 19e9ce0](https://github.com/gureev1988-ops/iikuznica/tree/19e9ce0ea4a8b6426a60ffe40f84ee85dc6fd789). В ней есть `DocumentSource.list_pages/probe`, `PageSnapshot`, каталог версий и фрагментов, `DocumentSync`, PostgreSQL-очередь `documents.sync` и ручной запуск. Композиция в `backend/app.py` создаёт по одному `confluence` и `batch`. Новая работа — конфиг именованных подключений, адаптер `http_json`, общий таймер и диагностика по подключению. Карта кода — `backend/config.py`, `backend/app.py`, `backend/documents/{ports,sync,catalog,router,confluence}.py`, `backend/runtime`, `docs/backend/run.md`.

## 1. Граница модуля

У подключения есть постоянный `source_key`, тип адаптера, настройки, признак включения и интервал. Каждый экземпляр получает собственные учётные данные, расписание и результат. Реестр типов — обычное отображение имени в фабрику внутри приложения. Владельцу выгрузки достаточно опубликовать файл по указанному ниже контракту. Для источника со своим протоколом разработчик добавляет адаптер и его регистрацию. Динамическая установка плагинов, отдельный сервис, брокер и интерфейс администратора за рамками пакета.

Адаптер поставляет данные в существующий каталог как `document`. Ядро получает те же идентификаторы документа, редакции и фрагмента, по которым сегодня проверяется цитата. Ответы службы качества продолжают идти через отдельный почтовый сценарий и FAQ. Документ или ссылка из выгрузки не получают статус разъяснения. Параметры поиска, разрешение противоречий, движок ответов, дизайн и демосценарии принадлежат отдельным пакетам.

## 2. Как подготовить подключение

1. Владелец выбирает согласованный набор документов, который может целиком читать каждый сотрудник. Выгрузки со смешанными правами требуют отдельного адаптера с поддержкой ACL. Убедиться, что по ссылкам можно открывать именно исходные материалы. Назначить владельца выгрузки и частоту публикации.
2. Подготовить один полный UTF-8 JSON. Система-источник присваивает документу постоянный строковый `id` и положительную целую `revision`. Любое изменение заголовка, текста или ссылки повышает редакцию. Переименование сохраняет `id`. Всё издание каталога также имеет положительный целый `snapshot_revision`. Повысить его при добавлении, изменении или исключении документа. Перестановка одних и тех же записей допустима в том же выпуске. При изменении документа повысить обе версии. Никогда не переиспользовать номер для другого содержимого, в том числе при возврате к старой редакции: восстановление оформляется новым выпуском по действующим правилам версий. Публиковать файл атомарно только после успешной сборки всего каталога. Временная неполнота оформляется ошибкой выгрузки. Пример целого файла:

```json
{
  "schema_version": 1,
  "snapshot_revision": 14,
  "complete": true,
  "count": 1,
  "documents": [
    {
      "id": "instruction-17",
      "revision": 2,
      "title": "Порядок регистрации заявки",
      "text": "Сотрудник регистрирует заявку в журнале.",
      "source_url": "https://kb.example.test/instructions/17"
    }
  ]
}
```

3. Разместить файл на согласованном HTTPS-адресе внутри доступного приложению контура. При необходимости выдать токен только на чтение. В `II_CONFIG` профиля `integrated` добавить блок ниже, а переменную с токеном задать в окружении API и фонового воркера. Используются отдельная база и конфигурация профиля. Пример показывает фрагмент конфигурации:

```json
{
  "profile": "integrated",
  "integrations": {
    "document_sources": {
      "instructions": {
        "type": "http_json",
        "enabled": true,
        "interval_seconds": 86400,
        "settings": {
          "url": "https://feeds.example.test/instructions.json",
          "bearer_token_env": "II_INSTRUCTIONS_READ_TOKEN",
          "audience": "all_employees"
        }
      }
    }
  }
}
```

4. Применить миграции (`python -m backend migrate`), запустить или перезапустить API (`python -m backend api`) и фоновый воркер (`python -m backend background`) с одинаковым конфигом. Для первой проверки удобно указать `interval_seconds: null` и включить расписание после ручной приёмки. Следующие команды относятся к реализуемому API и должны попасть в проверенную инструкцию при поставке. `API_BASE` содержит адрес API без суффикса `/v1`, `OPS_TOKEN` — токен оператора.

```sh
curl -fsS -H "Authorization: Bearer $OPS_TOKEN" "$API_BASE/v1/ops/documents/connections"
curl -fsS -X POST -H "Authorization: Bearer $OPS_TOKEN" "$API_BASE/v1/ops/documents/instructions/check"
curl -fsS -X POST -H "Authorization: Bearer $OPS_TOKEN" "$API_BASE/v1/ops/documents/instructions/sync"
# Подставить run_id из ответа 202.
curl -fsS -H "Authorization: Bearer $OPS_TOKEN" "$API_BASE/v1/ops/documents/sync/$RUN_ID"
```

5. Проверить `completed`, время успешной синхронизации и число активных документов. Для контрольного документа взять `revision_id` и `fragment_id` из контрольной цитаты либо из каталога тестовой БД, затем от имени сотрудника выполнить `GET /v1/sources/{revision_id}/fragments/{fragment_id}` и сверить точный текст. Внутренняя ссылка указывает на проверяемый фрагмент. `source_url` хранится в редакции как адрес оригинала. В рабочей инструкции дать пример чтения обоих ID из тестовой БД по `source_key` и `external_id` и запрос фрагмента с токеном сотрудника. Проверить повтор синхронизации, затем изменение одного документа с повышением редакции. Второй каталог такого же формата подключается новой записью в `document_sources` со своим ключом. Обе выгрузки обслуживает один и тот же адаптер.

## 3. Точный контракт

- В профиле `integrated` поддержать именованные `http_json`, `confluence` и `batch`. Существующие `integrations.batch` и `integrations.confluence` остаются рабочими с прежними ключами и ручным запуском. Для новых именованных подключений `enabled` по умолчанию true, интервал по умолчанию null (ручной режим), ненулевой интервал — целые секунды от 60. Повтор ключа, занятого прежним подключением, неизвестный тип и зарезервированные ключи локального корпуса отклонять с безопасным сообщением. Наследуемые ключи сохраняют данные и историю. Новый ключ обозначает отдельный набор данных. Переназначение существующего ключа другому корпусу запрещено операционной инструкцией.
- Для `http_json` обязательно явное `audience: all_employees`. Принимается ровно схема v1 из примера. Проверить типы, обязательные непустые значения, уникальность ID, положительную целую редакцию в диапазоне существующего столбца БД, `complete=true`, целый `count`, равный длине массива, и допустимый абсолютный HTTPS `source_url`. Неизвестные поля, в том числе ACL и признаки FAQ, отклонять. Учитывать ограничения сериализации PostgreSQL и текстового парсера. Ограничить потоковый ответ 2 МиБ после декодирования и 500 документами. Бюджет одного HTTP-запроса — 10 секунд общего времени. HTTP 200 и полный валидный JSON нужны для успешного чтения. Редиректы отключены. Запросы идут только на адрес из серверного конфига. Ссылки документов — данные для атрибуции, приложение их не обходит. Секреты, пользовательские данные в URL, содержимое выгрузки и сырые ошибки исключаются из логов и ответов диагностики. Ссылка на env-переменную необязательна, при заданной ссылке и отсутствующем значении обращение завершается ошибкой конфигурации без анонимного запроса.
- Преобразовать запись в `PageSnapshot`: `id → external_id`, `revision → version`, `source_url → upstream_url`. Текст — plain text. Преобразование в `storage_html` детерминировано, экранирует разметку и сохраняет границы абзацев. Для публикации использовать штатные индексирование, активацию и ссылки. Идентичность документа задаётся парой `(source_key, external_id)`. Один ID из двух подключений даёт два документа. Повтор одинаковой версии не создаёт редакций. Снижение версии или изменение текста, заголовка либо ссылки при прежней версии — ошибка каталога. Сверять с максимальной сохранённой версией, включая ранее снятые документы. Полная, явно опубликованная пустая выгрузка снимает все документы только этого подключения. Отозванные документы уходят из доступного для новых ответов корпуса. История и чтение прошлых ссылок подчиняются существующим правилам каталога.
- Для JSON проверить **весь** снимок, включая совместимость версий с БД, до первой публикации и обработки отсутствующих документов. При принятии первого снимка сохранить по ключу максимальную принятую `snapshot_revision` и SHA-256 канонического содержимого. Для равенства сравнивать валидированные записи по всем полям, включая URL, в порядке `id` с одинаковой UTF-8 JSON-сериализацией, независимо от пробелов и порядка ключей входного файла. При следующих чтениях принимать равную редакцию только при совпадении содержимого. Младший выпуск и равный с другим содержимым отклонить целиком, даже если валиден и пуст. Сохранять номер и хеш после очистки временного снимка. Завершение run и очистку фиксировать одной транзакцией. В одной транзакции сохранить в PostgreSQL номер, хеш и временный снимок под `run_id` до первого изменения каталога. Выбор и сохранение производить под штатной блокировкой данного источника. Список, проверки пропусков и возобновление после падения используют один сохранённый снимок. Внешний файл может успеть измениться между попытками. Внутри запуска повторных сетевых чтений для каждого документа нет. Успешное завершение освобождает временный снимок. Если импорт остановился после публикации части валидных данных, штатные контрольные точки позволяют завершить тот же снимок. Ошибка транспорта, формата или конфликта версии до сохранения оставляет весь прежний корпус доступным. На следующей попытке можно загрузить исправленную выгрузку. Пагинация внешнего JSON и частичные выгрузки выходят за пределы v1.

## 4. Расписание, диагностика и границы отказа

- Один периодический обработчик в существующем фоновом процессе выбирает наступившие `next_due_at` (UTC) для включённых подключений с интервалом. В PostgreSQL атомарно заказать/найти `documents.sync` и сдвинуть срок на текущее время плюс интервал. Переиспользовать транзакционную часть `request_sync`. Несколько воркеров, ручной запуск в ту же секунду и перезапуск дают максимум один незавершённый run на ключ. При регистрации, перезапуске и при выборе срока проверять конфигурацию текущего профиля. Первый срок для нового расписания — через интервал после регистрации. После простоя поставить один пропущенный запуск. Активный run покрывает наступивший срок. Смена интервала пересчитывает срок один раз. Ручной запуск сам расписание не сдвигает. Ограничить число подключений, рассматриваемых за проход, выбирать сначала давно ожидающие, разрешать независимую работу остальных. Фактическую загрузку выполняет очередь `background` с существующим пределом параллелизма, сроком аренды и ограниченными повторами. В обработчике расписания нет сетевого I/O.
- Таймаут источника не останавливает остальные подключения, почту, запросы сотрудников и готовность API. Сбой исчерпывает штатные повторы, оставляет run в `incomplete` и безопасную причину. Ручной запуск либо очередной интервал возобновляет его. Пауза (`enabled=false`) выключает новые проверки и запуски, убирает следующий срок. Эксплуатационный порядок — дождаться завершения активного запуска, затем отключить подключение и перезапустить процессы. Уже опубликованные общедоступные документы при паузе остаются в каталоге. Для намеренного снятия данных сначала опубликовать полный снимок с нужными исключениями и дождаться успешного завершения.
- Добавить `GET /v1/ops/documents/connections` для разрешённых профилем настроенных подключений. Ответ по каждому ключу включает тип, включение, интервал, следующий срок UTC, `last_check_at` и результат проверки, `last_success_at` для синхронизации, последний run (ID, состояние, безопасный код ошибки) и число активных документов. Допустимы null до первого события. Развести доступность подключения, актуальность корпуса и состояние последней попытки. Поддержать существующие агрегаты интеграций с учётом типа, даже когда нет ключа с буквальным именем `confluence`. Проверку готовности приложения не связывать с доступностью внешнего адреса.
- Добавить операторский `POST /v1/ops/documents/{source_key}/check`. Проверка выполняет ограниченное чтение реального ресурса без импорта, изменения фрагментов, планирования и вызова модели. JSON проверяет доступ и схему целой ограниченной выгрузки, Confluence — чтение в настроенной области, batch — валидность локального набора. Успех и ошибка возвращают диагностический результат (`200`, `ok`, `checked_at`, `error_code`, null при успехе). Обновляются только поля последней проверки. `DocumentSource.probe(id)` остаётся проверкой отдельной страницы. Итоговый sync фиксирует собственное состояние. `POST /{source_key}/sync` и `GET /sync/{run_id}` под тем же префиксом сохраняют контракт v0.3.1. Все эти маршруты используют `require_ops`. Неизвестное или скрытое подключение — 404, явная пауза для check/sync — 409.
- Профиль `hackathon` продолжает использовать прежнюю конфигурацию и локальный разрешённый корпус. Новые сетевые подключения игнорируются до разрешения env-секретов и создания клиентов, не попадают в расписание, выдачу, диагностику и историю доступных запусков. Сохранить существующий ручной импорт локального batch и его изоляцию на уровне каталога. Продуктовый фронтенд, демонстрационные данные и стенд не входят в поставку.

## 5. Приёмка и поставка

| Автоматическая проверка | Наблюдаемый результат |
|---|---|
| Два JSON-подключения с разными токенами, одинаковым ID и разными текстами, одно без расписания | Два независимых документа и статуса. Каждый адрес получил только свой токен. Ручной запуск доступен обоим. Автоматически запускается только одно. |
| Один файл, повтор, новая версия, пропуск и полное обнуление | Повтор сохраняет ID версии и фрагмента. Новая версия доступна после индексации. Исключённое исчезает из свежей выдачи, второе подключение сохраняется. Обычный фрагмент и его цитата читаются существующим путём, тип документа остаётся прежним. |
| Неверный JSON, дубли, таймаут, 401, редирект, слишком большой ответ, `complete=false`, неверный count, подмена версии в конце файла | Ноль преждевременных активаций/снятий. Безопасная ошибка видна у нужного источника. Исправленный ответ принимается следующей попыткой. |
| После нового издания сервер вернул старую пустую выгрузку или старый список с ранее снятым документом. Номер последнего издания повторён с другим составом | Все три ответа отклоняются без изменения каталога. Повтор эквивалентного содержимого с тем же номером допускается. Более новое намеренное обнуление принимается. |
| Сбой после обработки первого документа или перед сверкой пропусков, процесс перезапущен, ответ сервера уже другой | Run возобновляет тот же сохранённый снимок, без смешения версий, ложного снятия и дубликатов. Новый файл подхватит следующий run. |
| Два фоновых процесса, одновременный ручной запуск, просрочка после простоя, отказ одного источника | Единственный активный run на ключ и сдвиг срока ровно один раз. После исчерпания повторов отсутствует непрерывный перезапуск. Другой источник, почтовая задача и интерактивный обработчик отрабатывают. У фоновых задач допустимо ожидание свободного слота. Проверить на PostgreSQL. |
| Операторская проверка при прежнем успешном sync, пустая БД, пауза и запрос обычного сотрудника | Проверка обновляет только своё время/результат. Сбой сохраняет время последнего успешного sync. Пустое состояние различимо, пауза следует контракту, без роли ops доступ закрыт. |
| Старый конфиг Confluence/batch, профиль hackathon со вставленным тестовым сетевым конфигом, регрессии каталога | Сохраняются старые ключи и источники, в hackathon ноль внешних запросов и утечек метаданных. Проверить фиктивным транспортом и существующими тестами профиля. Штатная публикация и отзыв доверенного FAQ сохраняют свои правила при появлении/снятии документа с совпадающим заголовком. |

Новые сетевые сценарии проверять воспроизводимым HTTP-транспортом с синтетическими данными и реальным PostgreSQL для транзакций. Запустить существующий набор тестов бэкенда. Привести команды, результаты и ограничения проверки в PR. Если у прикладной системы нет штатного экспорта v1, описать подготовку преобразователя у владельца или добавление адаптера на `DocumentSource`, настройки области чтения, преобразования ID/версий/ссылок, проверки соединения и теста повторного импорта. Доступ в инфраструктуру заказчика для автоматической приёмки не требуется.
